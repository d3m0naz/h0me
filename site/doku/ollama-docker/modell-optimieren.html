Stock-Modell → Hermes-optimiertes Modell

Erzeugt aus addme.md am 21.11.2026

Anleitung, um aus einem Ollama-Modell eine Variante wie coder-64k zu bauen, die in Hermes zuverlässig Tool-Calls ausführt. Vorbild ist coder-64k = qwen3-coder:30b + 64k Kontext + 8 Threads, plus passende Sampling-Werte über einen benannten Provider in Hermes.

Platzhalter:

  • <basis>: das Stock-Modell, z. B. qwen3-coder:30b
  • <name>: die neue Variante, z. B. coder-64k
  • <provider>: der benannte Provider in Hermes, z. B. ollama-local

Alle Befehle laufen in ~/docker/ai-stack.

#Schritt 1: Basis-Modell wählen und laden

Auf der CPU kommt nur ein MoE-Modell in Frage (z. B. 30B gesamt, 3B aktiv). Dichte Modelle ab ~14B sind für Agenten zu langsam. Bevorzugt das offizielle Ollama-Paket nehmen, nicht hf.co/....

bash
docker compose exec ollama ollama pull <basis>

#Schritt 2: Tool-Support und Parser prüfen

bash
docker compose exec ollama ollama show <basis>                    # unter Capabilities muss "tools" stehen
docker compose exec ollama ollama show <basis> --modelfile \
  | grep -E "^(FROM|RENDERER|PARSER|TEMPLATE)"
ErgebnisBedeutungWeiter mit
RENDERER … und PARSER … vorhandenOllama erkennt das Tool-Call-Format des ModellsSchritt 3
Nur TEMPLATE bzw. template source go_template, kein ParserTypisch für HF-GGUFs. Tool-Calls kommen unter langem Prompt oft als JSON-TextSchritt 2a
Kein tools unter CapabilitiesModell ist für Hermes ungeeignetanderes Modell

#Schritt 2a: Renderer/Parser nachrüsten (nur bei HF-GGUFs)

Das geht nur, wenn das GGUF zur selben Modellfamilie gehört wie ein offizielles Paket mit Parser. Dann muss es dasselbe Tool-Call-Format gelernt haben. Welche Werte passen, zeigt das offizielle Paket der Familie:

bash
docker compose exec ollama ollama show qwen3-coder:30b --modelfile | grep -E "^(RENDERER|PARSER)"
# RENDERER qwen3-coder
# PARSER qwen3-coder

Diese beiden Zeilen kommen in Schritt 3 zusätzlich ins Modelfile. Ein Qwen3-Coder-Parser auf einem Modell einer anderen Familie (z. B. Qwen3.5/3.6, Gemma) ist geraten. Er funktioniert nur, wenn das Format zufällig übereinstimmt. Der Praxistest in Schritt 7 entscheidet.

#Schritt 3: Modelfile schreiben und Variante erzeugen

bash
docker compose exec ollama sh -c '
  printf "FROM <basis>\nPARAMETER num_ctx 65536\nPARAMETER num_thread 8\n" > /tmp/Modelfile &&
  ollama create <name> -f /tmp/Modelfile'
ZeileWarum
FROM <basis>Übernimmt Gewichte, Template, RENDERER und PARSER des Basis-Modells. Es wird nichts kopiert, die Blobs werden geteilt
PARAMETER num_ctx 65536Hermes verlangt mindestens 64k Kontext, sonst gibt es einen Kontextfehler beim Start
PARAMETER num_thread 8Physische Kerne des 5700G, nicht die 16 Threads
bei 2a zusätzlich: RENDERER … / PARSER …Tool-Call-Erkennung für HF-GGUFs

Keine Sampling-Werte (temperature, top_p) ins Modelfile schreiben, um Hermes damit zu steuern. Ollamas OpenAI-Endpunkt /v1 ignoriert sie und setzt 1.0, wenn der Client nichts mitschickt. Die Werte kommen in Schritt 5 in die Hermes-Config.

#Schritt 4: Variante prüfen

bash
docker compose exec ollama ollama show <name>                                  # tools, context length
docker compose exec ollama ollama show <name> --modelfile | grep -E "^(FROM|RENDERER|PARSER|PARAMETER)"

Erwartet sind RENDERER und PARSER (geerbt oder ergänzt), dazu num_ctx 65536 und num_thread 8.

Schnelltest über die OpenAI-API:

bash
curl -s http://localhost:11434/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "<name>",
  "temperature": 0.7, "top_p": 0.8,
  "messages": [{"role": "user", "content": "What is the weather in Berlin?"}],
  "tools": [{"type": "function", "function": {"name": "get_weather",
    "description": "Get current weather for a city",
    "parameters": {"type": "object", "properties": {"city": {"type": "string"}},
    "required": ["city"]}}}]
}' | jq '.choices[0].message'

Erwartet: "content": "" und ein tool_calls-Array. Dieser Test ist notwendig, aber nicht hinreichend. Er nutzt einen Mini-Prompt, Hermes schickt ~6.000 Token.

RAM: Mit OLLAMA_NUM_PARALLEL=2 bekommt jeder Slot den vollen num_ctx. Der KV-Cache reicht also für 2×64k. Bei Qwen3-Coder-30B-A3B sind das geschätzt ~12 GB zusätzlich zu ~19 GB Gewichten. Nach dem ersten Laden mit docker compose exec ollama ollama ps prüfen.

#Schritt 5: Hermes-Config anpassen

Zuerst prüfen, welche Blöcke es schon gibt. Doppelte Top-Level-Schlüssel überschreiben sich stillschweigend:

bash
grep -n "^providers:\|^model:\|^agent:\|^auxiliary:" hermes-data/config.yaml

Dann in hermes-data/config.yaml direkt in der Datei ändern (hermes config set hatte zeitweise keine Wirkung):

yaml
providers:
  <provider>:
    api: http://ollama:11434/v1        # Service-Name, nie localhost
    extra_body:
      temperature: 0.7                 # empfohlene Werte des Modells (Model Card)
      top_p: 0.8

model:
  default: <name>
  provider: custom:<provider>
  • Sampling-Werte aus der Model Card des Modells nehmen. Für Qwen3-Coder sind das 0.7 / 0.8. Bei Temperatur 1.0 kamen die Tool-Calls als JSON-Text.
  • Hat ein weiteres Modell andere Empfehlungen, bekommt es einen zweiten benannten Provider mit eigenem extra_body, statt den ersten zu ändern.
  • auxiliary.*.provider: main und agent.disabled_toolsets gelten unabhängig vom Modell (siehe README, Abschnitt 3). Bei einem neuen Stack einmalig setzen.

Kontrolle:

bash
docker compose exec hermes hermes config get model
docker compose exec hermes hermes config get providers

#Schritt 6: Hermes neu starten und Modell aktivieren

bash
docker compose up -d hermes                  # nur Hermes, Ollama behält das Modell im RAM
docker compose exec -it hermes hermes

Im Chat:

/model custom:<provider>:<name>
/reasoning none --global
/new
  • /model immer mit custom:<provider>: angeben. Sonst greift extra_body nicht, und es kommt Temperatur 1.0 an.
  • /reasoning none --global nur bei Modellen ohne Thinking (Qwen3-Coder). Sonst gibt es einen 400-Fehler does not support thinking.
  • /new ist Pflicht. Alte Sessions mit fehlerhaften Aufrufen werden vom Modell nachgeahmt.

#Schritt 7: Praxistest in Hermes

Im Chat: „Liste alle Dateien in /workspace auf.“

Der erste Turn dauert mit kaltem Cache etwa 1,5 Minuten. Nicht abbrechen. Erfolg heißt: Hermes führt den Befehl aus und zeigt die Dateiliste, nicht einen Text wie {"name": "terminal", …}.

Parallel in einem zweiten Terminal die Ollama-Logs prüfen:

bash
docker compose logs ollama --since 5m | grep -E "temp =|top_p|truncated|n_ctx_slot|cached n_tokens|task.n_tokens"

Zum Schluss auf Warnungen prüfen:

bash
docker compose exec hermes hermes logs --level WARNING

Hier darf weder nous_auth_missing noch does not support thinking auftauchen.

#Schritt 8 (optional): In OpenCode eintragen

In opencode.json unter provider.ollama.models:

json
"<name>": {
  "name": "<Anzeigename>",
  "limit": { "context": 65536, "output": 16384 },
  "options": { "temperature": 0.7, "top_p": 0.8 }
}

Beide Clients sollten dasselbe Modell nutzen. Sonst laufen zwei Runner mit doppelten Gewichten, und bei OLLAMA_MAX_LOADED_MODELS=2 verdrängt das small_model eines davon.

#Kurzfassung (am Beispiel coder-64k)

bash
docker compose exec ollama ollama pull qwen3-coder:30b
docker compose exec ollama ollama show qwen3-coder:30b --modelfile | grep -E "^(RENDERER|PARSER)"
docker compose exec ollama sh -c '
  printf "FROM qwen3-coder:30b\nPARAMETER num_ctx 65536\nPARAMETER num_thread 8\n" > /tmp/Modelfile &&
  ollama create coder-64k -f /tmp/Modelfile'
docker compose exec ollama ollama show coder-64k --modelfile | grep -E "^(RENDERER|PARSER|PARAMETER)"
# config.yaml: providers.ollama-local.extra_body {temperature: 0.7, top_p: 0.8}, model.default coder-64k
docker compose up -d hermes
# Im Chat: /model custom:ollama-local:coder-64k → /reasoning none --global → /new → Praxistest
docker compose logs ollama --since 5m | grep -E "temp =|top_p|truncated"
