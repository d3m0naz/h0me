Lokaler KI-Stack: Ollama + OpenCode + Hermes Agent

Erzeugt aus README.md am 21.11.2026

Ein vollständig lokaler KI-Stack in Docker Compose. Alle Modelle laufen auf der eigenen Hardware, ohne Cloud-API und ohne dass Daten das Netzwerk verlassen.

KomponenteAufgabe
OllamaLLM-Server, stellt eine OpenAI-kompatible API bereit (http://ollama:11434/v1)
OpenCodeCoding-Agent im Terminal (TUI), arbeitet in /workspace
Hermes AgentAutonomer Agent von Nous Research mit persistentem Gedächtnis, Skills und Messaging-Gateway, arbeitet ebenfalls in /workspace

Hardware: AMD Ryzen 7 5700G (8 Kerne, Zen 3, AVX2), 2×32 GB DDR4-3200 Dual-Channel, kein Swap, keine GPU. Reine CPU-Inferenz.

Referenz-Setup, Werte auf der genannten Hardware gemessen.

#2. Modellwahl: warum MoE

Auf der CPU begrenzt die Speicherbandbreite die Textgenerierung. Pro erzeugtem Token müssen alle aktiven Gewichte einmal aus dem RAM gelesen werden. DDR4-3200 Dual-Channel schafft real etwa 35–40 GB/s.

ModelltypBeispielGenerierungPrompt-Verarbeitung
Dense 27B (Q4, ~16 GB)Qwen 27B~1,5–2,5 Token/s~10–25 Token/s
MoE 30B, 3B aktiv (Q4_K_M, ~19 GB)Qwen3-Coder-30B-A3B~20 Token/s (kleiner Kontext)~40–110 Token/s

Ein dichtes 27B-Modell ist für agentisches Arbeiten zu langsam. Agenten schicken große System-Prompts mit Tool-Definitionen mit, und deren Verarbeitung dauert dann viele Minuten. Mixture-of-Experts-Modelle aktivieren pro Token nur einen kleinen Teil ihrer Parameter und sind auf der CPU um ein Vielfaches schneller.

#Eingesetztes Modell

VerwendungModellHinweis
Basisqwen3-coder:30bOffizielles Ollama-Paket mit eigenem Renderer und Parser für Tool-Calls
Hermes (und OpenCode)coder-64kAbgeleitete Variante mit num_ctx 65536 und num_thread 8
OpenCode small_modelqwen2.5-coder:1.5bFür Nebenaufgaben wie Titelgenerierung

Wichtig: Verwende das offizielle Ollama-Paket, nicht das GGUF von Hugging Face (hf.co/...). Nur das offizielle Paket bringt RENDERER qwen3-coder und PARSER qwen3-coder mit. Mit dem generischen Template aus dem HF-GGUF werden Tool-Calls bei langem Kontext nicht zuverlässig erkannt (siehe Fallstudie 11.1).

#Alternativen

ModellGesamt / aktivRAM (Q4)Hinweis
Qwen3.5-35B-A3B (auch abliteriert: huihui_ai/qwen3.5-abliterated:35b)35B / 3B~21 GBNeuere Generation mit Thinking. Tool-Parser vor dem Einsatz prüfen
Gemma 4 26B-A4B abliterated26B / 4B~15 GBEtwas langsamer, neigt im Thinking-Modus zu Endlosschleifen

Abliterierte (unzensierte) Modelle: Abliteration entfernt die Ablehnungsrichtung aus den Gewichten. Das kann die Qualität und die Zuverlässigkeit von Tool-Aufrufen leicht verschlechtern. Vor dem Einsatz mit Hermes immer ollama show <modell> --modelfile auf RENDERER/PARSER prüfen und den Tool-Call-Test durchführen. Fehlen die Zeilen, kann man sie per eigenem Modelfile ergänzen (FROM <gguf> + RENDERER qwen3-coder + PARSER qwen3-coder) und dann in Hermes praktisch testen.

#compose.yaml

yaml
services:
  ollama:
    image: ollama/ollama:latest
    restart: unless-stopped
    ports:
      - 11434:11434                  # offen im LAN; sicherer: 127.0.0.1:11434:11434
    volumes:
      - ollama:/root/.ollama
    environment:
      OLLAMA_CONTEXT_LENGTH: "32768" # Standard für Modelle ohne eigenes num_ctx
      OLLAMA_KEEP_ALIVE: "24h"       # Modell nicht nach 5 Min. entladen
      OLLAMA_NUM_PARALLEL: "2"       # 2. Slot, damit Nebenanfragen den Prompt-Cache nicht verdrängen
      OLLAMA_MAX_LOADED_MODELS: "2"  # höchstens zwei Modelle gleichzeitig im RAM

  opencode:
    build:
      context: .
      dockerfile: opencode.Dockerfile
    profiles: ["cli"]                # startet nicht bei "up", nur per "run"
    depends_on: [ollama]
    working_dir: /workspace
    stdin_open: true
    tty: true
    volumes:
      - ./workspace:/workspace
      - ./opencode.json:/home/node/.config/opencode/opencode.json:ro
      - opencode-data:/home/node/.local/share/opencode

  hermes:
    image: nousresearch/hermes-agent:latest
    container_name: hermes
    command: gateway run
    depends_on: [ollama]
    restart: unless-stopped
    shm_size: 1g                     # für Browser-Tools
    environment:
      - HERMES_UID=${HERMES_UID:-1000}
      - HERMES_GID=${HERMES_GID:-1000}
      - HERMES_API_TIMEOUT=1800      # CPU-Inferenz ist langsam
    volumes:
      - ./hermes-data:/opt/data
      - ./workspace:/workspace       # gleicher Projektordner wie OpenCode

volumes:
  ollama:
  opencode-data:

Hinweise:

  • Kein network_mode: host. Hermes und OpenCode erreichen Ollama über den Service-Namen ollama im Bridge-Netz. Im Host-Netz gibt es diesen Namen nicht, dann brechen Chat und Tool-Calls ab. Für SSH zu anderen Rechnern ist das Host-Netz ebenfalls nicht nötig.
  • Keine Mounts nach /root. Hermes läuft als UID 1000, seine Daten liegen in /opt/data. OpenCode läuft als User node (ebenfalls UID 1000).
  • Der Container ollama heißt ohne container_name automatisch ai-stack-ollama-1.

#opencode.Dockerfile

dockerfile
FROM node:22-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends git ripgrep ca-certificates curl \
    python3 python3-pip python3-venv python-is-python3 shellcheck \
 && rm -rf /var/lib/apt/lists/* \
 && npm i -g opencode-ai
USER node
RUN mkdir -p /home/node/.config/opencode /home/node/.local/share/opencode
CMD ["opencode"]
  • USER node hat die UID 1000, wie Hermes und der Host-User. Alle drei können deshalb in workspace/ schreiben.
  • Das mkdir als node sorgt dafür, dass das Volume opencode-data beim ersten Start mit dem richtigen Besitzer angelegt wird.
  • npm i -g opencode-ai hat keine feste Version. Jeder build holt die neueste.
  • CMD, nicht ENTRYPOINT: Argumente bei docker compose run ersetzen den ganzen Befehl. Deshalb muss opencode immer mitgeschrieben werden, z. B. docker compose run --rm opencode opencode -c. Eine Shell bekommst du mit docker compose run --rm opencode bash.

#4.1 Ollama starten und Modell laden

bash

Prüfen, dass Tool-Support und der eigene Parser vorhanden sind:

bash

64k-Variante anlegen:

bash
docker compose exec ollama sh -c '
  printf "FROM qwen3-coder:30b\nPARAMETER num_ctx 65536\nPARAMETER num_thread 8\n" > /tmp/Modelfile &&
  ollama create coder-64k -f /tmp/Modelfile'

Warum genau diese Parameter, wie man prüft, dass Renderer und Parser geerbt wurden, und wie das mit anderen Modellen geht, steht Schritt für Schritt in der Anleitung zum Modell-Optimieren.

#4.2 Erster Test

bash
docker compose exec -it ollama ollama run coder-64k --verbose

Nach jeder Antwort zeigt --verbose die prompt eval rate (Einlesen) und die eval rate (Generierung). /bye beendet.

Tool-Calling über die OpenAI-kompatible API testen (diesen Endpunkt nutzen auch OpenCode und Hermes):

bash
curl -s http://localhost:11434/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "coder-64k",
  "messages": [{"role": "user", "content": "What is the weather in Berlin?"}],
  "tools": [{"type": "function", "function": {"name": "get_weather",
    "description": "Get current weather for a city",
    "parameters": {"type": "object", "properties": {"city": {"type": "string"}},

Erwartet: "content": "" und ein gefülltes tool_calls-Array mit "name": "get_weather".

#4.5 Hermes Agent

Setup-Wizard ausführen:

bash
export HERMES_UID=$(id -u) HERMES_GID=$(id -g)
docker compose run --rm hermes setup

Im Wizard:

  1. Full setup wählen. Quick Setup würde Nous Portal, also Cloud-Modelle, einrichten. Für maximale Geschwindigkeit ist Blank Slate die schlankere Alternative.
  2. Provider: Custom Endpoint
  3. Base URL: http://ollama:11434/v1
  4. API Key: leer oder no-key
  5. Model: coder-64k
  6. Nicht benötigte Tools (Web-Suche, Bildgenerierung, TTS, Messaging) überspringen.

Config nachbearbeiten: Den model:-Block in hermes-data/config.yaml durch die Blöcke providers:, model:, agent: und auxiliary: aus Abschnitt 3 ersetzen bzw. ergänzen. Kontrolle:

bash
docker compose exec hermes hermes config get auxiliary | grep provider   # überall "main"

Gateway starten:

bash
docker compose up -d hermes
docker compose exec hermes curl -s http://ollama:11434/v1/models
docker compose exec hermes ls -la /workspace                            # Projektdateien sichtbar?

Reasoning abschalten. Im Hermes-Chat einmalig:

/reasoning none --global

Prompt-Größe messen:

bash
docker compose exec hermes hermes prompt-size --json

Ziel ist etwa 6.000 Token (siehe Fallstudie 11.2).

Praxistest: Im Chat /new eingeben, dann „Liste alle Dateien in /workspace auf.“ Der erste Turn dauert auf der CPU etwa 1,5 Minuten (Prefill). Erfolg: Hermes führt den Befehl aus und antwortet mit der Dateiliste, nicht mit einem JSON-Text.

Kontrolle in den Ollama-Logs, dass die Sampling-Werte ankommen:

bash
docker compose logs ollama --since 2m | grep -E "temp =|top_p"
# erwartet: top_p = 0.800 ... temp = 0.700

opencode gehört zum Profil cli und startet bei docker compose up nicht mit. docker exec als root wird im Hermes-Image automatisch auf den hermes-User umgeleitet, ein --user ist nicht nötig.

#6. Sessions verwalten

#OpenCode

Sessions liegen im Volume opencode-data und überleben neue Container.

bash
# Sessions auflisten
docker compose run --rm opencode opencode session list

# Bestimmte Session fortsetzen
docker compose run --rm opencode opencode -s <session-id>

An einen laufenden OpenCode-Container anhängen, z. B. von einem zweiten Terminal:

bash
docker ps --filter name=opencode
docker attach <container-name>

Lösen ohne Beenden mit Ctrl+P, dann Ctrl+Q (nicht Ctrl+C). Wird der Bildschirm danach falsch angezeigt, das Terminalfenster einmal in der Größe ändern.

#Hermes

Sessions, Memories und Skills liegen in hermes-data/. Niemals zwei Hermes-Gateways auf dasselbe Datenverzeichnis laufen lassen, das beschädigt Sessions und Memories. Für Chats daher immer docker compose exec in den laufenden Container verwenden, nie parallel docker compose run.

#7. Modelle verwalten

bash
# Modell aus der Ollama-Bibliothek laden (bevorzugt, bringt Parser mit)
docker compose exec ollama ollama pull <modell>

# Modell aus Hugging Face laden (Parser fehlt oft!)
docker compose exec ollama ollama pull hf.co/<user>/<repo>:<quant>

# Renderer/Parser prüfen
docker compose exec ollama ollama show <modell> --modelfile | grep -E "^(FROM|RENDERER|PARSER|TEMPLATE)"

# Kurzen Alias vergeben
docker compose exec ollama ollama cp <quelle> <alias>

# Alle Modelle anzeigen / entfernen
docker compose exec ollama ollama list
docker compose exec ollama ollama rm <modellname>

Ollama teilt Daten-Blobs zwischen Namen. Speicherplatz wird erst frei, wenn alle Namen (Original und Aliase) eines Modells entfernt sind.

Gleichzeitig geladene Modelle: OLLAMA_MAX_LOADED_MODELS=2 erlaubt zwei Modelle im RAM. Für Ollama sind qwen3-coder:30b und coder-64k zwei verschiedene Modelle, auch wenn sie dieselben Gewichte nutzen. Nutzen Hermes und OpenCode unterschiedliche Modelle und kommt das small_model dazu, entlädt Ollama eines davon. Am besten nutzen beide Clients coder-64k.

Nach einem Modellwechsel opencode.json bzw. hermes-data/config.yaml anpassen und in Hermes eine neue Session starten (/new). Modelle mit anderen empfohlenen Sampling-Werten bekommen in Hermes einen eigenen benannten Provider mit passendem extra_body. Den kompletten Ablauf für ein neues Modell beschreibt die Anleitung zum Modell-Optimieren.

#8. Performance

#Gemessene Werte (Qwen3-Coder-30B-A3B Q4_K_M, 5700G)

Kleiner Prompt (~250 Token)~55–110 Token/s~20 Token/s< 3 s
Erster Hermes-Turn, volle Toolsets (~15–17k Token, kalter Cache)~39 Token/s2,4–4,7 Token/s~5 Minuten
Erster Hermes-Turn, reduzierte Toolsets (6.011 Token, kalter Cache)~62 Token/s8,96 Token/s (Stichprobe von 10 Token)97 s

Die Generierung bricht mit großem Kontext deutlich ein. Weniger fester Prompt bedeutet daher nicht nur kürzeren Prefill, sondern auch schnellere Tokens. Lange Antworten wie ganze Code-Dateien dauern trotzdem. Das ist die CPU-Grenze, kein Fehler.

#Ollama / Hardware

  • num_thread 8 setzen: physische Kerne, nicht die 16 Threads.
  • OLLAMA_NUM_PARALLEL=2: Ohne zweiten Slot verdrängt jede kleine Nebenanfrage den großen Agenten-Prompt aus dem Cache, und der nächste Turn dauert wieder lange. In den Logs ist das an saving prompt with length … zu erkennen. Folge-Turns einer Hermes-Session landen im selben Slot, der Cache greift also.
  • OLLAMA_KEEP_ALIVE=24h verhindert das Entladen zwischen Anfragen.
  • Einen NVIDIA-deploy-Block weglassen, solange keine GPU vorhanden ist. Die integrierte Vega-8-GPU bringt praktisch nichts: Ollama unterstützt sie nicht offiziell, und sie hängt am selben RAM.
  • RAM im BIOS auf das XMP-/DOCP-Profil stellen. Mehr MT/s ergeben direkt mehr Token/s.
  • Bei knappem Speicher halbieren OLLAMA_FLASH_ATTENTION=1 und OLLAMA_KV_CACHE_TYPE=q8_0 ungefähr den KV-Cache.

#Hermes

Hermes schickt bei jedem Aufruf einen festen System-Prompt plus die Schemas aller aktiven Tools. Das ist der größte Hebel für die Geschwindigkeit:

bash
docker compose exec hermes hermes prompt-size --json     # Größe messen
docker compose exec -it hermes hermes tools              # Toolsets verwalten

Dauerhaft geht das über agent.disabled_toolsets in config.yaml (Abschnitt 3). title_generation und background_review sind abgeschaltet, weil sie nach jedem Turn zusätzliche Anfragen auslösen.

#9. Arbeiten mit Hermes: Prompt-Tipps

Gewonnen beim Bau eines Beispiel-Scripts in zwei Schritten, PLAN und BUILD.

  • Arbeitsverzeichnis festlegen: Im Prompt den Zielordner nennen (z. B. /workspace/<projekt>), absolute Pfade verlangen und zuerst pwd ausführen lassen.
  • Englisch prompten: Qwen3-Coder folgt englischen Prompts zuverlässiger als deutschen.
  • Plan prüfen, nicht neu planen: Der erste Plan war brauchbar, ließ aber Lücken, die ein kleines Modell beim Build falsch auslegt. Lücken als „Additional constraints (they override the plan where it differs)“ in den BUILD-Prompt schreiben. Eine weitere Planungsrunde kostet auf der CPU viel Zeit.
  • Konkret statt vage: Formulierungen wie „based on severity“ oder „per Shell-Funktion mocken“ durch exakte Regeln ersetzen (welcher Fall FAIL, welcher WARN, welche Variable, welches Format).
  • Selbstprüfung verlangen: bash -n, shellcheck, ein Testlauf mit einem erreichbaren und einem unerreichbaren Host (192.0.2.1), Exit-Code und ls -la am Ende anzeigen lassen. shellcheck ist im OpenCode-Image installiert.
  • Temperatur: Für Build-Aufgaben gelten 0.2–0.4 als günstiger. Im Stack ist 0.7 eingestellt und für Tool-Calls getestet. Wer niedriger gehen will, legt einen zweiten benannten Provider an und testet die Tool-Calls erneut. Temperatur 1.0 bricht die Tool-Calls (Fallstudie 11.1).
  • SSH aus Hermes: Hermes läuft als UID 1000, nicht als root. SSH-Keys gehören ins Home dieses Users (docker compose exec hermes sh -c 'echo $HOME'). Ein Test gegen localhost klappt nur, wenn der Key aus dem Container in authorized_keys auf dem Host steht. Sonst ist FAIL dort das erwartete Ergebnis.
  • Nach jeder Korrektur /new: Alte Sessions mit fehlerhaften Aufrufen werden vom Modell nachgeahmt.

#11. Fallstudien

#11.1 Tool-Calls zum Laufen bringen

Das Symptom: Auf „Liste alle Dateien in /workspace auf“ antwortete Hermes mit einem Text wie

{"name": "terminal", "arguments": {"command": "find . -type f ... | sort"}}

statt den Befehl auszuführen. Das Modell wollte das Tool aufrufen, aber Ollama erkannte die Ausgabe nicht als Tool-Call und reichte sie als normalen Antworttext weiter. Die Lösung bestand aus mehreren Bausteinen, die alle nötig waren.

Diagnoseweg:

  1. Modell und API isoliert testen (Curl-Test aus 4.2): Sowohl /api/chat als auch /v1/chat/completions lieferten saubere tool_calls.
  2. Truncation ausschließen: Ollama-Logs zeigten n_ctx_slot = 65536, task.n_tokens = 12144, truncated = 0.
  3. Anfrager identifizieren: Über docker inspect die IP des Hermes-Containers zugeordnet.
  4. Hermes-Logs lesen: Sie zeigten die Nous- und Reasoning-Fehler.
  5. Modelfile prüfen: Das HF-GGUF hatte nur ein generisches Template (template source go_template), keinen eigenen Parser.
  6. Sampling-Parameter in den Ollama-Logs prüfen: temp = 1.000, top_p = 1.000, obwohl das Modell 0.7 / 0.8 vorsieht.
#UrsacheLösung
119 Hilfsaufgaben (u. a. approval, der Shell-Befehle vor der Ausführung prüft) fragten Nous Portal anauxiliary.*.provider: main
2Reasoning-Anfrage an ein Modell ohne Thinking (400-Fehler)/reasoning none --global

4Ollamas OpenAI-API setzt Temperatur und top_p auf 1.0, wenn der Client keine Werte mitschickt. Die Modelfile-Werte gelten dort nicht. Bei 1.0 und langem Prompt wich das Modell vom trainierten XML-Format auf nacktes JSON ausBenannter Provider mit extra_body: {temperature: 0.7, top_p: 0.8}
5Die alte Session enthielt die fehlerhaften JSON-Aufrufe, die das Modell nachahmteNach jeder Korrektur /new

Der entscheidende letzte Baustein war die Temperatur: Mit neuem Parser, aber Temperatur 1.0 kam weiterhin JSON-Text.

Merksätze:

  • Ein erfolgreicher Curl-Test mit Mini-Prompt beweist nicht, dass Tool-Calls unter einem langen Agenten-Prompt funktionieren.
  • Modelfile-Parameter (temperature, top_p) gelten nicht automatisch für die OpenAI-kompatible API. In den Ollama-Logs unter sampler params nachsehen, was wirklich ankommt.
  • Bei einem Modellwechsel in Hermes immer /model custom:ollama-local:<modell> verwenden, sonst greift extra_body nicht.

#11.2 Hermes-Prompt verkleinern

Die Generierung stieg von 2,37 auf 8,96 Token/s und der kalte Prefill sank von ~5 Minuten auf 97 s, nachdem acht ungenutzte Toolsets abgeschaltet waren. Vorher hatte Hermes mit jeder Anfrage ~58 KB System-Prompt und Tool-Definitionen geschickt. Hardware, Modell und Threads waren nicht die Ursache.

#11.3 Leerer Workspace

Hermes meldete /workspace als leer. Die Ursache: OpenCode mountete ./work:/work, Hermes ./workspace:/workspace. Die Projektdateien lagen in ./work. Docker hatte workspace/ beim ersten Start als root angelegt, Hermes hätte dort also nicht einmal schreiben können.

Lösung: Hermes gestoppt, den leeren Ordner entfernt, work in workspace umbenannt, Besitzer auf UID 1000 gesetzt und OpenCode auf ./workspace:/workspace umgestellt. Ergebnis: pwd in Hermes zeigt /workspace, die Projektdateien sind sichtbar.

bash
docker compose stop hermes
sudo rmdir workspace
mv work workspace
sudo chown -R 1000:1000 workspace
docker compose up -d hermes

Ein früher Vorschlag mit network_mode: host und Mounts nach /root wurde verworfen. Mit dem Host-Netz bricht die Verbindung zu Ollama ab, und Hermes läuft nicht als root.
